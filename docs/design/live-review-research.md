# Build the live-review overlay on agent-browser

No mature tool, as of October 2026, lets a human and Claude Code review a running local web app together in the way described: the agent marks elements in a headed browser, the human comments on the page, and the notes come back into the same terminal session through a CLI. The closest match is **FinalAngel/claude-annotate**. It is MIT-licensed, injects an overlay into any localhost URL and paints agent progress back onto pins, but it has **1 star and 1 contributor**, and push delivery depends on Claude Code's research-preview "channels" flag ([README](https://github.com/FinalAngel/claude-annotate)). **Agentation** has the richest two-way protocol (acknowledge, reply, resolve, dismiss), but it must be mounted as a React component in the app and is licensed **PolyForm Shield** ([repo](https://github.com/benjitaylor/agentation)). **Lavish** has the cleanest poll/reply contract, but it only opens local `.html` files ([artifact-path.js](https://github.com/kunchenguid/lavish-axi/blob/main/src/artifact-path.js)). The hands-on tests show that agent-browser already provides every building block. A 60-line init script survived navigation, captured Alt+click notes, sent them to a local HTTP inbox, and showed agent replies injected with `eval`. The recommendation is therefore to build a small vega-owned overlay on agent-browser that copies Lavish's poll/reply contract and reuses the design ideas of claude-annotate and pinpoint, not their code. Adopting a tool is not recommended until one of them matures.

## Hands-on: agent-browser already carries the whole loop

The coordinator tested this on the local machine on 2026-10-10, with agent-browser 0.31.1 installed (upstream is at v0.39.0) and lavish-axi 0.1.85. These results carry more weight than any README claim below.

**agent-browser covers injection, the page-to-agent channel and the agent-to-page channel.** A script registered with `--init-script overlay.js open <url>` ran before the page's own JavaScript, and it was still present after navigating to a second page. The 60-line plain-JS prototype turned Alt+click into a prompt and stored a note `{selector, url, text, rect, ts}` in three places: a window buffer, a tagged `console.log("VEGA_NOTE …")`, and a `fetch` POST to a Python inbox on 127.0.0.1:5199. The POST used `text/plain`, so there was no CORS preflight. All three channels worked headless. `agent-browser console` showed the tagged line, but the buffer also held logs from an earlier page in the session, so console scraping needs a filter. `agent-browser eval 'window.__vegaReply("…")'` rendered an agent reply in the overlay panel.

**Three problems turned up in testing, and they shape the design.** First, the built-in `highlight` is useless for review: a red 2px outline with no label, gone after about 3 seconds. The source confirms a hard-coded `setTimeout(…, 3000)` ([interaction.rs](https://github.com/vercel-labs/agent-browser/blob/main/cli/src/native/interaction.rs)). Persistent, labelled highlights need the overlay's own `window.__vegaHighlight(sel, label)` called through `eval`. Second, `agent-browser wait --fn 'window.__vegaReview.notes.length > 0'` works as a long-poll: it returns the moment the page adds a note. But the session daemon serializes commands, so while that wait blocks, `eval`, `highlight` and `get url` queue behind it. The agent cannot poll and annotate at the same time. **The poll target must be a separate inbox process, not the browser session.** Third, the window buffer is lost on full navigation, so the HTTP inbox (or sessionStorage) has to hold the durable state.

Neither agent-browser's `dashboard start` (port 4848) nor its `stream enable` is a commenting surface. The dashboard is a Next.js observability UI with a live view and a command feed. The stream is a WebSocket carrying screen frames and input, not a channel for events from page JavaScript.

**Lavish's contract works as designed, but only for files.** In the test, the agent-browser session typed a message in Lavish's conversation panel and clicked Send to Agent. `lavish-axi poll <file>` then returned at once with `status: feedback`, `prompts[]{uid,prompt,selector,tag,text}` and a `dom_snapshot`, and feedback queued before the poll started was still delivered. `lavish-axi reply --agent-reply` returned an acceptance receipt. Clicking an element in Annotate mode via automation produced no popover; this was not pursued further. Two defaults need attention. **The server listened on the Tailscale IP as well as on loopback**, so it was reachable from the whole tailnet. **Umami telemetry is on unless `LAVISH_AXI_TELEMETRY=0` is set.** A vega-built inbox should bind to loopback only and send no telemetry.

A practical caution: port 5187 was already serving the owner's live Spire app during the tests, so the test site moved to 5287. Any tooling should pick ports dynamically, not hard-code them.

**The popular tools are popular for the wrong half of the loop.** Agentation does the hard part: blocking `agentation_watch_annotations`, then `acknowledge`, `reply` and `resolve`, with resolved notes disappearing from the browser over SSE ([session-resolutions.ts](https://github.com/benjitaylor/agentation/blob/main/package/src/utils/session-resolutions.ts)). But it needs a React app and edits to the app's source, and its PolyForm Shield license forbids use in a competing product. Whether its toolbar shows agent replies inline is unverified; the code confirms only resolved and dismissed statuses. Playwright's `browser_annotate` is the closest off-the-shelf piece. It returns an annotated screenshot, an ARIA snapshot and the list of notes in a single tool result. Its notes, though, are rectangles on a captured frame in a dashboard window, recorded as pixel coordinates, not as DOM elements in the live page. The tool call also blocks the agent until the human submits ([annotate.spec.ts](https://github.com/microsoft/playwright/blob/main/tests/mcp/annotate.spec.ts)). Playwright's `page.pickLocator()` (since v1.59) is the cleanest "human clicks, agent gets a locator" primitive, but it is a library API that requires a Node driver ([class-page.md](https://github.com/microsoft/playwright/blob/main/docs/src/api/class-page.md)).

**Commercial tools fail on locality.** Every vendor MCP server, from Jam and BugHerd to Usersnap and Vercel, is hosted and gated behind OAuth, even when the browser extension can capture localhost ([Usersnap](https://help.usersnap.com/docs/mcp-connector), [BugHerd](https://support.bugherd.com/en/articles/14835206-getting-started-with-the-bugherd-mcp-server)). **Consumer AI browsers are a dead end.** OpenAI shut down Atlas on 2026-08-09 ([Wikipedia](https://en.wikipedia.org/wiki/ChatGPT_Atlas)). Opera Neon's MCP connector is relayed through Opera's proxy ([Opera press](https://press.opera.com/?p=3885)). None of them offers element-anchored comments for an external agent. WebMCP is still a Chrome origin trial (M149–M156), and its API has already changed mid-trial ([blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/gmYffo5WOE8/m/OJxuQRP3AAAJ?hl=el)), so it is not a foundation to build on.

## The gap: a DOM-bound, two-way, CLI-polled overlay for any local URL

No tool combines all six properties the workflow needs:

1. It injects into an arbitrary running dev server without source changes or a framework requirement.
2. It anchors comments to live DOM elements, not screenshot pixels.
3. The agent can draw persistent, labelled highlights.
4. Agent replies and statuses render on the page.
5. Notes reach the existing Claude Code session through a CLI long-poll with receipts, not only MCP or the clipboard.
6. It shares the browser session the agent already drives.

claude-annotate meets the first four, but it launches its own Chrome, speaks only MCP and depends on a research-preview flag. Agentation fails on the first property and on licensing. Lavish fails on the first. pinpoint and Feedback Studio meet the first two, but their write-back paths are undocumented or thin, and both are a few weeks old.

**The sixth property matters more than it looks.** If the review overlay lives in a second browser, the agent's existing agent-browser refs, cookies and navigation state do not carry over. The agent ends up highlighting in one window while the human comments in another. agent-browser's `--init-script`, `--extension` and `eval` let the overlay live in the agent's own session ([README](https://github.com/vercel-labs/agent-browser)).

## Three options, ranked

**Option A: adopt claude-annotate.** This is the fastest route to a working loop: `/annotate http://localhost:5287/`, then pins, replies and progress states. It costs nothing to try, and its MIT license allows forking. The downsides: it is a single-maintainer project with one star, its push delivery requires `--dangerously-load-development-channels` (with admin enablement on Team or Enterprise plans), and its fallback is a blocking MCP tool. It also brings its own playwright-core browser, separate from agent-browser. Use it as a one-afternoon experiment and a reference implementation, not as a dependency.

**Option B: combine agent-browser with an existing extension.** agent-browser's `--extension <path>` could load pinpoint (MIT) into the agent's own session. Human comments would then flow through pinpoint's local bridge (127.0.0.1:7331) and its Claude Code hook or `.pinpoint/pending.md`, while the agent highlights through `eval` ([pinpoint](https://github.com/gowtham012/pinpoint)). A variant swaps pinpoint for Playwright MCP's `browser_annotate` when screenshot-level feedback is enough. This combination is untested: nobody has verified that pinpoint runs inside an agent-browser session, and agent replies would still not appear on pinpoint's pins. It glues together two young or mismatched tools and still leaves agent-to-page rendering to be written.

**Option C: build a vega-owned overlay on agent-browser with a Lavish-style contract (recommended).** The hands-on work has already proven every piece:

- **Overlay.** An init script, mounted in a shadow DOM so the app's CSS cannot leak in, handles Alt+click comments, `__vegaHighlight(sel, label)` for persistent agent marks, and `__vegaReply(id, text, status)` for threads.
- **Inbox.** A loopback-only `vega` inbox process receives the overlay's `text/plain` POSTs and keeps notes across navigations.
- **Agent interface.** An AXI CLI (`vega review poll|reply|end`) copies Lavish's semantics: one listener per session, `--owner`/`--takeover`, notes queued until delivered and consumed on delivery, a `next_step` hint, and Seen/Working/Done receipts that come from what the server observes ([lavish-axi CLI reference](https://github.com/kunchenguid/lavish-axi#cli-reference)).

Polling the inbox, not `agent-browser wait --fn`, keeps the browser session free for highlighting. The MIT building blocks are small: `@medv/finder` for selectors (1.6 KB gzipped) and `@floating-ui/dom` for popovers ([finder](https://github.com/antonmedv/finder)). Notes should store CSS, XPath and text anchors together, as SitePing does, so they survive hot reloads ([SitePing](https://github.com/NeosiaNexus/SitePing)). Screenshots should be clipped natively through agent-browser, not rasterized from the DOM. The approach fits the repo's AXI principles and needs no MCP, no research-preview flag and no app changes. Its costs are real: a few hundred lines to own, an injected `fetch` that a strict app CSP could block (the tagged console line is the fallback), and no push into an idle session. The agent still has to be polling, which is the same constraint every tool except claude-annotate's channels mode accepts.

**Recommendation: Option C, informed by a short Option A spike.** Spend an hour with claude-annotate to borrow its UX: pin states, the dev-host allow-list, and the PostToolUse hook that shows which file is being edited. Then build C. Agentation is ruled out by its license and its source-install requirement. The Option B combination does not save enough to justify depending on a three-star extension.

## Conclusion

The market has converged on the human-to-agent half of this workflow, with a dozen ways to click an element and send a selector to an agent, and has largely skipped the agent-to-human half. Persistent agent highlights and in-page replies exist only in Agentation (source install, restrictive license) and claude-annotate (one star, preview flag). The decisive discovery is architectural, not about any product. The browser session cannot double as the message queue, because agent-browser serializes commands, so a durable poll/reply contract belongs in a separate inbox. Lavish has already designed and battle-tested that contract; it only lacks a live-URL front end. Building that front end on agent-browser is the cheapest way to fill the gap.

Several points remain open. The pinpoint-inside-agent-browser combination is untested. Whether Agentation's toolbar renders reply threads is unverified. Whether Claude Code's channels feature will leave research preview, which would make push delivery viable for a vega tool too, is unknown.
